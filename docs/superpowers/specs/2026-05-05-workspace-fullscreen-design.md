## 0. 文档说明

### 0.1 目的

为当前应用的工作区页增加一个原生浏览器全屏能力：

- 桌面端：在设置按钮右侧新增全屏切换按钮
- 移动端：在设置按钮右侧新增全屏切换按钮
- 全屏状态下，同一个按钮切换为退出全屏
- 桌面端保留 `Escape` 退出原生全屏

本次设计只解决“工作区页原生全屏”的交互与状态模型，不扩展到设置页、欢迎页或其他非工作区页面。

### 0.2 背景

当前工作区已经具备：

- 桌面端顶栏工具区，包含设置按钮
- 移动端顶栏动作区，包含设置按钮
- 桌面端应用内专注模式
- 移动端多种全屏 sheet 交互

但尚未提供浏览器原生全屏入口。用户需要一个低摩擦、可发现、跨桌面与移动端心智一致的方式进入全屏工作区。

在前期讨论中，已经明确以下约束：

1. 全屏能力采用 **浏览器原生 Fullscreen API**
2. 按钮仅在 **工作区页** 显示
3. 按钮放在 **设置按钮右侧**
4. 桌面端允许 `Escape` 退出
5. 移动端若当前浏览器不支持原生全屏，则 **直接隐藏按钮**

### 0.3 设计目标

- 为工作区页提供统一的原生全屏切换入口
- 使用同一个按钮承载“进入全屏 / 退出全屏”两态
- 在桌面端和移动端维持一致的按钮位置和状态语义
- 不引入额外的移动端浮层、手势或二级退出机制
- 让按钮状态只依赖浏览器真实全屏状态，避免 UI 漂移
- 与现有专注模式、顶栏结构、移动端布局保持兼容

### 0.4 非目标

- **不**把全屏按钮扩展到 `/settings`、欢迎页或鉴权页面
- **不**把该能力做成应用内沉浸模式降级方案
- **不**为不支持 Fullscreen API 的移动端提供替代交互
- **不**在本次设计中新增快捷键进入全屏
- **不**自动在进入全屏时开启专注模式
- **不**在进入全屏时自动隐藏顶栏、侧栏、Dock 或终端面板

## 1. 方案比较

### 1.1 方案 A：系统退出为主，按钮仅用于进入全屏

用户进入全屏后，不在应用内提供显式退出按钮，退出完全依赖桌面端 `Escape`、浏览器 UI 或移动端系统手势。

优点：

- 实现最轻
- 不需要按钮双态切换

缺点：

- 移动端可发现性较差
- 用户需要记住系统级退出方式
- 与“按钮放在设置右侧”的入口心智不闭环

### 1.2 方案 B：进入/退出使用两个独立按钮

非全屏态显示“进入全屏”，全屏后额外展示另一个“退出全屏”按钮，可能以悬浮条或额外动作区形式出现。

优点：

- 语义直观
- 可为退出态增加更强视觉强调

缺点：

- 会破坏当前顶栏动作区的简洁结构
- 移动端需要额外设计浮层或退出条
- 进入与退出路径分散，不如单一 toggle 清晰

### 1.3 方案 C：同一个按钮在两态之间切换（推荐）

默认显示“进入全屏”；处于原生全屏时，同一位置切换为“退出全屏”。桌面端同时保留 `Escape` 退出，移动端则以按钮退出为主。

优点：

- 桌面端和移动端语义完全一致
- 按钮位置固定，可发现性强
- 不需要额外退出 UI
- 能与浏览器原生 `fullscreenchange` 事件天然对齐

缺点：

- 需要把全屏目标设置为包含顶栏的工作区根容器
- 需要明确与专注模式的 `Escape` 优先级

### 1.4 最终选择

采用 **方案 C**。

理由：

- 用户已经接受“按钮就在设置右边”的空间约束，最自然的补全方式就是让该位置承载完整的进入/退出闭环
- 同一按钮切换状态比“进入按钮 + 系统退出”更稳定，也比“进入按钮 + 额外退出浮层”更克制
- 该方案能同时兼顾 PC 与移动端，而不需要为移动端额外创造一套退出语法

## 2. 最终设计

### 2.1 信息架构与显示范围

全屏按钮仅在工作区页渲染：

- 桌面端：工作区桌面布局页
- 移动端：工作区移动布局页

不在以下页面渲染：

- 设置页
- 欢迎页
- 登录或鉴权相关页面
- 任何非工作区顶层页面

按钮位置固定为：

- 桌面端：设置按钮右侧
- 移动端：设置按钮右侧

### 2.2 全屏目标容器

全屏目标必须是 **包含顶栏的工作区根容器**，而不是只包中间内容区。

建议目标：

- 桌面端：`WorkspaceDesktopView` 中的 `.workspace-page`
- 移动端：`WorkspaceMobileView` 中的 `.mobile-shell`

这样做的原因是：

1. 进入全屏后，顶栏仍然存在
2. 顶栏中的全屏按钮可以原地切换为退出全屏
3. 用户不需要在全屏后重新寻找退出入口

如果只对工作区主体内容做全屏，顶栏会从可视区域中消失，按钮双态设计将无法成立，因此本方案不采用局部内容全屏。

### 2.3 共享状态模型

全屏能力应建模为 **工作区级共享状态**，而不是由桌面端按钮或移动端按钮各自维护一份本地布尔值。

建议抽象为共享 controller 或 hook，例如：

- `useWorkspaceFullscreen(targetRef)`

最小暴露面：

- `supported`
- `isFullscreen`
- `enterFullscreen()`
- `exitFullscreen()`
- `toggleFullscreen()`

状态来源规则：

- 不单独持久化“猜测中的全屏状态”
- `isFullscreen` 只基于浏览器真实状态计算
- 监听 `fullscreenchange` 作为唯一状态同步入口

这样可以覆盖以下退出路径：

- 用户点击退出全屏按钮
- 桌面端按下 `Escape`
- 浏览器或系统主动结束全屏

无论哪条路径发生，按钮都能回到一致的“进入全屏”状态。

### 2.4 支持与隐藏策略

按钮只在以下条件同时满足时显示：

1. 当前页面是工作区页
2. 当前运行环境支持 Fullscreen API
3. 当前工作区根容器存在且可作为全屏目标

其中移动端有额外策略：

- 若当前移动端浏览器不支持原生 Fullscreen API，则 **直接隐藏按钮**
- 不弹错误提示
- 不显示不可用态按钮
- 不自动降级到应用内沉浸模式

该策略的目标是保持界面简洁，并避免向用户暴露“看得到但点不了”的控制项。

### 2.5 按钮交互规则

按钮为严格的双态切换按钮。

未全屏时：

- 图标表示“进入全屏”
- `aria-label` / `title` 为“进入全屏”
- 点击后对工作区根容器调用 `requestFullscreen()`

已全屏时：

- 图标表示“退出全屏”
- `aria-label` / `title` 为“退出全屏”
- 点击后调用 `document.exitFullscreen()`

实现上不要求按钮自己预测切换结果：

- 如果 `requestFullscreen()` 失败，按钮仍保持“进入全屏”
- 只有在 `fullscreenchange` 确认进入后，按钮才切换到“退出全屏”

### 2.6 桌面端行为

桌面端全屏交互规则如下：

- 通过顶栏按钮进入全屏
- 通过同一按钮退出全屏
- 通过 `Escape` 也可退出原生全屏

桌面端进入全屏后，不自动改变应用布局：

- 顶栏保留
- 左侧栏保留原状态
- 底部终端面板保留原状态
- 当前打开的编辑器、Agent 面板或 diff 视图保持不变

换句话说，原生全屏只改变浏览器展示层级，不额外重排应用内部布局。

### 2.7 移动端行为

移动端全屏交互规则如下：

- 通过顶栏按钮进入全屏
- 通过同一按钮退出全屏
- 若浏览器或系统自身退出全屏，按钮通过 `fullscreenchange` 自动回切

移动端进入全屏后，同样不自动改写应用布局：

- 顶部栏保留
- 底部 Dock 保留
- 当前 Agent 区、文件 sheet、终端 sheet 等维持原状态

本次设计明确 **不** 增加以下附加退出机制：

- 下滑退出
- 双击退出
- 顶部临时悬浮退出条
- 进入全屏后的额外一次性提示层

移动端的应用内主退出路径只有一个：同一位置的退出全屏按钮。

### 2.8 与专注模式的关系

原生全屏与现有专注模式是两个不同层级的概念：

- 原生全屏：浏览器展示状态
- 专注模式：应用内部布局状态

本次设计中二者保持独立：

- 进入原生全屏时，不自动开启专注模式
- 退出原生全屏时，不自动关闭专注模式
- 进入或退出专注模式时，也不自动影响原生全屏状态

用户可以同时处于“原生全屏 + 专注模式”。

### 2.9 `Escape` 优先级

桌面端 `Escape` 的优先级必须明确，避免与专注模式冲突。

规则如下：

1. 如果当前处于 **原生全屏**，按下 `Escape` 时优先退出原生全屏
2. 只有在 **不处于原生全屏**、但仍处于 **专注模式** 时，`Escape` 才退出专注模式

因此，当用户同时开启“原生全屏 + 专注模式”时：

- 第一次 `Escape`：退出原生全屏
- 第二次 `Escape`：退出专注模式

这一规则保证浏览器层状态优先于应用层状态，也与用户对系统级 `Escape` 的普遍预期一致。

### 2.10 可访问性与文案

按钮需要提供明确、与当前状态一致的可访问性文案：

- 未全屏：`进入全屏`
- 已全屏：`退出全屏`

可访问性要求：

- 桌面端与移动端都提供 `aria-label`
- 桌面端保留 `title`
- 图标切换必须与语义一致，避免“视觉看起来仍是进入态，但实际行为是退出态”

不额外增加“按 Escape 退出”等说明型 tooltip，以避免文案噪音。

### 2.11 异常处理

可能的异常包括：

- 浏览器拒绝全屏请求
- 全屏目标容器为空
- 环境在渲染期间不再支持 Fullscreen API

处理原则：

- 不切换到错误的 UI 状态
- 不弹侵入式错误提示
- 用户界面保持当前可理解状态

推荐行为：

- `requestFullscreen()` 失败时保留“进入全屏”态
- `exitFullscreen()` 失败时等待后续浏览器状态事件，不强制本地回写
- 开发期可输出 `console.warn` 便于排查

## 3. 组件与实现边界

### 3.1 组件落点

建议在以下位置接入按钮：

- 桌面端顶栏：`packages/web/src/features/topbar/index.tsx`
- 移动端顶栏：`packages/web/src/features/workspace/views/mobile/mobile-topbar.tsx`

建议在以下容器上挂载全屏目标 ref：

- `packages/web/src/features/workspace/views/desktop/workspace-desktop-view.tsx`
- `packages/web/src/features/workspace/views/mobile/workspace-mobile-view.tsx`

### 3.2 推荐实现拆分

推荐形成三个清晰边界：

1. `useWorkspaceFullscreen`
   - 管理浏览器 Fullscreen API 交互
   - 监听 `fullscreenchange`
   - 暴露 `supported` / `isFullscreen` / `toggleFullscreen`

2. `WorkspaceFullscreenButton`
   - 只负责根据状态渲染图标、文案和点击行为
   - 不直接关心桌面端或移动端布局

3. 工作区页面容器集成
   - 负责提供 target ref
   - 负责把 fullscreen controller 传给顶栏按钮

### 3.3 状态归属

以下状态应归属于共享 controller：

- 当前是否支持全屏
- 当前是否处于原生全屏
- 当前全屏目标是否就是当前工作区根容器

以下状态不应新增：

- 本地持久化的“用户偏好是否默认全屏”
- 桌面端单独一套 `isDesktopFullscreen`
- 移动端单独一套 `isMobileFullscreen`

## 4. 测试与验证要求

### 4.1 单元与组件测试

需要覆盖以下核心场景：

1. 支持 Fullscreen API 且未全屏时，按钮渲染为“进入全屏”
2. 处于全屏时，按钮渲染为“退出全屏”
3. `fullscreenchange` 触发后，按钮状态同步更新
4. 移动端不支持 Fullscreen API 时，不渲染按钮
5. 点击进入全屏时，调用目标容器的 `requestFullscreen()`
6. 点击退出全屏时，调用 `document.exitFullscreen()`
7. `requestFullscreen()` 失败时，按钮不误切换到退出态

### 4.2 集成行为测试

桌面端需验证：

- 按钮出现在设置按钮右侧
- 进入全屏后仍可通过同一按钮退出
- `Escape` 退出原生全屏后，按钮回切为进入态
- 同时开启专注模式时，`Escape` 先退出原生全屏，再退出专注模式

移动端需验证：

- 按钮出现在设置按钮右侧
- 进入全屏后按钮切换为退出态
- 浏览器不支持时按钮完全不显示
- 系统或浏览器退出全屏后，按钮同步回切

### 4.3 回归重点

需要重点关注以下回归风险：

- 顶栏按钮顺序被打乱
- 设置按钮行为被影响
- 专注模式现有 `Escape` 行为被破坏
- 移动端顶栏宽度不足导致按钮拥挤或截断
- 终端 sheet / 文件 sheet 在全屏状态下出现布局异常

## 5. 结论

本次设计采用工作区级原生 Fullscreen API 能力，并用一个放置在设置按钮右侧的双态按钮完成进入/退出闭环。

最终规则总结如下：

- 仅工作区页显示
- 同一个按钮在“进入全屏 / 退出全屏”之间切换
- 桌面端支持按钮退出与 `Escape` 退出
- 移动端以按钮退出为主
- 移动端不支持原生全屏时直接隐藏按钮
- 全屏目标覆盖包含顶栏的工作区根容器
- 进入全屏后不自动重排应用布局
- `Escape` 优先退出原生全屏，其次才退出专注模式

这一方案在实现成本、交互一致性和可发现性之间取得了最稳妥的平衡，适合作为当前工作区全屏能力的第一版设计。
