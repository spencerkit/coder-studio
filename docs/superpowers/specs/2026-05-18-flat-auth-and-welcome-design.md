> **版本：** 1.0
> **日期：** 2026-05-18
> **状态：** Draft（待评审）

## 0. 文档说明

### 0.1 目标

对以下三个入口页面做一轮统一的扁平化重设计：

- `/login`
- `/session-gate`
- 登录后的首页欢迎页，即 `WelcomePage`

本轮目标不是改业务流程，而是把这三个页面从当前偏“独立大卡片 + 渐变/浮起”的入口页语言，收拢为与 PC 端更一致的产品式页面语言：

- 保留大标题和入口页识别度
- 去掉过重的 glow、渐变、厚阴影和浮起感
- 建立更清晰的分段结构
- 让登录页、会话门页、欢迎页共享同一套页面语气

### 0.2 本轮范围

包含：

- 三个页面的 DOM 分区调整
- 三个页面的视觉层级重做
- 桌面端与移动端响应式规则调整
- 现有单元测试 / 样式测试补强
- 预览截图更新

不包含：

- 认证接口、跳转逻辑、状态机逻辑修改
- i18n 文案体系重构
- 通用 Button / Input 组件 API 重写
- 其他 workspace / settings 页面结构改版

### 0.3 当前结构

当前页面主要依赖如下组件和样式：

- `packages/web/src/features/auth/index.tsx`
- `packages/web/src/features/auth/session-gate.tsx`
- `packages/web/src/features/welcome/index.tsx`
- `packages/web/src/styles/components.css`

当前三页已经复用部分入口页壳层：

- 外层容器：`welcome-container` / `auth-screen`
- 卡片壳：`welcome-card` / `auth-card-shell`
- 欢迎页分区：`welcome-card__hero` / `welcome-card__actions` / `welcome-card__panel`

这给本轮改版提供了较好的基础：可以重做结构和层级，但不需要推翻已有页面骨架。

### 0.4 现状问题

当前问题集中在五点：

1. `welcome-container` 和 `auth-screen` 的背景仍以大面积 radial gradient 为主，入口页有明显“海报化”倾向，与 PC 端产品页不一致。
2. `welcome-card` 和 `auth-card-shell` 仍然依赖较重圆角、较厚阴影和略显鼓起的面板处理，不够扁平。
3. 登录页和 `session-gate` 虽然已经共用基础壳层，但内部仍然更像“空状态 + 附加表单”，而不是结构清晰的产品入口页。
4. 欢迎页的 feature 区仍偏“营销卡片阵列”，不够像登录后首页，不利于与 PC 端应用气质对齐。
5. 移动端虽然已修复纵向伸展问题，但整体视觉语言仍沿用桌面营销卡片思路，单栏时会更明显地放大“浮起感”。

## 1. 设计目标与非目标

### 1.1 设计目标

- 保留“欢迎使用 coder studio”这一类大标题入口感
- 登录页、会话门页、欢迎页共享同一套扁平化语言
- 视觉重心从“整张大卡片”改为“卡内分段 + 轻面板”
- 输入框、按钮、状态区更接近 PC 端应用表单语言
- 错误和提醒状态更克制，不再显得过度告警
- 移动端沿用同一语言，但保持单栏阅读节奏

### 1.2 非目标

- 不新增认证步骤、辅助链接、密码重置等额外交互
- 不把欢迎页扩展成完整 dashboard
- 不引入新的主题家族或重新设计全局 token
- 不修改欢迎页按钮文案和基本操作路径

## 2. 方案选择

### 2.1 方案 A：保留现有中心大卡片，仅减弱渐变和阴影

优点：

- 改动最小
- 风险最低

缺点：

- 只能“变淡”，无法真正改变结构问题
- 登录页和欢迎页仍然会保留较强 landing page 感
- 很难和 PC 端应用页形成统一语言

### 2.2 方案 B：保留大标题，改成分段式轻面板入口页

优点：

- 保留当前欢迎页识别度
- 能把 hero、状态、操作、功能说明拆成稳定分区
- 最容易向 PC 端“应用首页”语气靠拢
- 登录页、会话门页、欢迎页可以共享相同的结构原则

缺点：

- 需要同时改 DOM 结构和 CSS
- 测试断言需要同步更新

### 2.3 方案 C：彻底做成紧凑设置页 / 系统页样式

优点：

- 最扁平
- 最接近工具产品

缺点：

- 会丢掉首页的大标题入口感
- 欢迎页会过于“功能面板化”，不够像进入产品后的首屏
- 与用户已认可的“欢迎页大标题”方向不符

### 2.4 结论

本轮采用 **方案 B：分段式轻面板入口页**。

选择原因：

- 它保留了用户认可的“欢迎页大标题”气质
- 它能显著削弱当前过重卡片感
- 它最适合作为 `/login`、`/session-gate`、`WelcomePage` 的共享结构语言

## 3. 共享设计语言

### 3.1 页面外层

三页继续共用入口页外层容器，但视觉规则重写：

- 保留 `welcome-container` / `auth-screen` 的全页居中职责
- 背景改为更浅、更贴近产品壳层的 page background
- 允许保留非常轻的方向性底纹或弱渐变
- 不再使用明显 glow、色块云雾或强烈光晕

结果应表现为：

- 页面仍有入口感
- 但更像产品应用首页，而不是宣传页

### 3.2 主面板

主内容区域统一收敛为“轻面板”：

- 使用实色 surface 为主
- 使用 1 层弱边框建立外轮廓
- 使用轻量阴影或无明显阴影
- 圆角从当前偏大的 `xl` 级别收敛到更克制的中大圆角

面板的重点不再是“整张卡片悬浮起来”，而是“内部内容被有序分段”。

### 3.3 分段结构

三页统一遵循以下结构原则：

1. Hero 区
2. 状态 / 辅助信息区
3. 操作区
4. 补充信息区（仅欢迎页保留）

这意味着：

- 登录页和 `session-gate` 不再只是空状态下面堆一个表单
- 欢迎页不再是一个大卡片内再塞几个浮卡

### 3.4 文本层级

文案层级统一如下：

- kicker：弱化，保留识别性，但不再主导视觉
- page title：最大层级，承担页面主识别
- description：作为辅助说明，宽度受控，不做居中长段宣传文案
- section label / status eyebrow：用于分段说明，采用小号 uppercase / meta 语气

### 3.5 扁平化规则

本轮三页统一遵循以下视觉约束：

- 不使用厚重投影
- 不使用玻璃感、模糊感、反射感
- 不使用高对比装饰性渐变按钮
- 不使用“独立漂浮小卡片 + 卡片内再卡片”的叠层
- 重点依靠：边框、留白、分组、字重、对齐来建立层级

## 4. `/login` 页面设计

### 4.1 信息结构

`/login` 调整为三段式：

1. Hero：`CODER STUDIO` kicker + 应用名大标题 + 简短说明
2. Status：当前认证状态、不可用状态、未配置状态、错误状态
3. Form：密码输入框 + 主确认按钮

现有 `auth-card-shell__content` 可继续保留，但内部需要明确划分区域，而不是只靠垂直堆叠。

### 4.2 视觉方向

- Hero 左对齐
- 状态区改成轻量信息面板，而不是醒目的告警块
- 表单区与状态区之间保持明确节奏
- 输入框和按钮更接近 PC 端设置/表单页语言

### 4.3 状态面板

状态面板规范：

- 默认状态使用中性 surface
- 不可用与错误状态只做轻度错误染色
- 通过边框和浅背景变化传递状态，不靠大面积红色
- `auth.status_title` 作为小型 section label 使用

### 4.4 表单区

表单区规范：

- 密码输入框和提交按钮形成单一动作组
- 两者宽度对齐
- 移动端保持上下堆叠
- 桌面端也保持单栏，不做并排，以维持专注入口感

### 4.5 页面结果

最终观感应当是：

- 一个大标题入口页
- 一块轻量状态信息区
- 一个克制、明确的认证动作区

而不是“宣传海报 + 大卡片 + 表单”。

## 5. `/session-gate` 页面设计

### 5.1 与 `/login` 的关系

`/session-gate` 直接复用 `/login` 的页面壳层、分段规则和间距体系。

用户应当一眼识别出：

- 这是同一产品的同一入口体系
- 只是当前状态从“首次输入密码”变成“会话失效，需要重新进入”

### 5.2 内容差异

与 `/login` 的关键区别：

- Hero 文案改为会话失效语义
- Status 区强调当前会话已失效或需要重新进入
- Form 区替换为单一主按钮，不展示密码输入框

### 5.3 视觉处理

- 不要把 `session-gate` 做成“报错页”
- 状态区使用轻度提醒语气
- 主按钮继续复用与登录页一致的主操作样式

这样能保证视觉一致性，也避免用户在重新进入流程中感到被强烈打断。

## 6. `WelcomePage` 设计

### 6.1 页面定位

`WelcomePage` 不是营销落地页，也不是复杂 dashboard。

它应当是一个登录后可快速开始工作的首页，承担三件事：

1. 欢迎用户进入产品
2. 提供主入口操作
3. 用简洁方式说明产品核心能力

### 6.2 信息结构

欢迎页调整为三段：

1. Hero：kicker + 大标题 + 简短说明
2. Actions：打开工作区主按钮 + 设置次按钮
3. Features：三个核心能力说明块

现有 `welcome-card__hero`、`welcome-card__actions`、`welcome-card__panel` 可以继续沿用，但整体改为更明显的“分段式首页面板”。

### 6.3 Hero

Hero 区原则：

- 保留大标题
- 从当前偏居中的展示，收敛为更像应用首页的排版
- 说明文案长度受控，不做大段宣传语

桌面端推荐：

- 主体内容左对齐
- 面板整体居中，但内容内部不必再完全居中

### 6.4 Actions

操作区原则：

- 主按钮保留高优先级
- 设置入口作为次级动作保留
- 按钮样式向 PC 端应用按钮收拢，不再强调“落地页 CTA”

桌面端建议为同组操作：

- 主按钮在前
- 次级按钮在后
- 组内间距清晰但不过度拉开

移动端：

- 保持纵向堆叠
- 主按钮全宽
- 次级动作不抢主入口焦点

### 6.5 Features

feature 区从当前“三张相对独立的浮起卡片”改为“同组轻量能力面板”。

具体规则：

- 保留三列信息结构
- 每项仍有图标、标题、说明
- 卡片本体改为轻边框、弱圆角、弱对比 surface
- 不使用明显浮起阴影
- 组内对齐更像应用首页的能力摘要，而不是 marketing highlight

桌面端：

- 三列展示
- 列高尽量整齐

移动端：

- 退化为单列
- 不强行保留三列比例

### 6.6 页面结果

欢迎页应当保留“欢迎使用 coder studio”的入口感，但整体更像产品首页：

- 有标题气质
- 有主动作
- 有能力摘要
- 没有悬浮营销卡片感

## 7. 响应式策略

### 7.1 桌面端

- 面板保持受控最大宽度
- 内容内部允许左对齐，减少当前“巨型居中卡片”感
- 欢迎页 feature 区保留三列
- 登录页和 `session-gate` 保持单栏窄面板，突出单一任务

### 7.2 移动端

- 延续已修复的单栏流式结构
- 所有模块纵向排列
- 欢迎页 feature 区改为单列
- 输入框和按钮保持满宽
- 安全区 padding 与现有移动壳层保持兼容

### 7.3 一致性原则

移动端不是桌面的缩小版，而是同一视觉语言的单栏展开：

- 同样的面板层级
- 同样的文本语气
- 同样的按钮和状态区规则
- 只是布局从分段宽版收敛为单列

## 8. 实现策略

### 8.1 结构改动策略

优先在现有组件结构上增量调整：

- `LoginPage`：保留当前 fetch / auth 逻辑，只重组内容分段
- `SessionGatePage`：复用同一壳层结构，只替换操作区内容
- `WelcomePage`：保留 modal 与导航行为，只调整 hero / actions / features 结构

### 8.2 样式改动策略

样式改动集中在 `packages/web/src/styles/components.css`：

- 重写 `welcome-container` / `welcome-card`
- 重写 `auth-screen` / `auth-card-shell`
- 调整欢迎页 actions / features 的布局和层级
- 同步更新对应 mobile 规则

### 8.3 风险控制

为降低风险，本轮不改变：

- 组件行为
- 路由行为
- 文案 key
- 表单提交流程

核心变化只聚焦在：

- DOM 分区
- class 组合
- CSS 层级

## 10. 验收标准

本轮完成后，应同时满足以下条件：

1. `/login`、`/session-gate`、`WelcomePage` 三页共享统一的扁平化入口页语言。
2. 大标题仍保留，但背景、卡片、feature 区不再有明显营销感或浮起感。
3. 登录页与 `session-gate` 的状态区更克制，错误态不过度刺眼。
4. 欢迎页更像登录后应用首页，而不是宣传型 landing page。
5. 移动端保持单栏且无布局拉伸问题。
6. 相关测试和预览可以稳定证明这轮改版结果。

## 11. 结论

本轮采用“**保留欢迎页大标题，但整体改成分段式扁平入口页**”的方向。

这条路径兼顾了三件事：

- 延续当前产品的入口识别度
- 与 PC 端应用气质对齐
- 降低三页样式割裂与未来维护成本

该设计已完成文本确认，下一步应在用户评审这份 spec 后，进入实现计划编写与代码落地阶段。
